AI can write a component in a few minutes. But who will notice that the component saves the wrong
data, breaks the keyboard on mobile, or makes a learner lose their answer after a refresh?

The engineer is still responsible. So learning Claude is not only learning to ask good questions. It
is learning to turn a request into a change that can be checked, understood and maintained.

This is an editorial guide, not official Anthropic material. Where I describe this site's own setup,
it is an accurate description of its repository. The other examples are illustrations, not measured
results from a real project.

## 1. Don't start by adding more agents

In "Building effective agents" (December 2024), Anthropic separates two kinds of systems. In a
**workflow**, a language model and its tools follow steps that a developer has defined in advance.
An **agent** decides its own steps and chooses which tools to use as it goes.

The advice is to find the simplest solution that works, and add complexity only when it is needed.
Agentic systems often trade more **latency** and cost for better results on hard tasks, so that trade
has to be worth it. For many applications, one well-prepared call to a model, with good examples and
the right information, is enough.

The same article describes common patterns. In *prompt chaining*, each step works on the output of
the step before. *Routing* sends each input to a specialised handler. *Parallelization* runs parts at
the same time, or runs the same task several times and compares the answers. In
*orchestrator-workers*, one model splits a task and hands the parts to others. In
*evaluator-optimizer*, one model writes and another gives feedback in a loop.

A 2026 post shows what that trade looks like in practice. In March, Prithvi Rajasekaran described a
set-up with three agents for building whole applications: a planner that writes a product spec, a
generator that builds the app, and an **evaluator** that clicks through the running app and grades
it. In one test, a single agent built a small game maker in 20 minutes for about $9, but its core
feature did not work. The three-agent version took six hours and cost about $200, and the result was
clearly better. More structure paid off there, but it cost more than 20 times as much.

The post adds a lesson that ages well: every extra part of such a set-up encodes an assumption about
what the model cannot do alone. Those assumptions go out of date as models improve, so the set-up
should be checked again when a new model arrives.

For a personal blog, the first question should be simpler: "What can the user not do right now?" If
learners cannot find a lesson, a clear button may help more than a team of agents.

My own rule follows from that. Only when the work splits cleanly into independent parts, and someone
is responsible for combining the results, should you add a second agent. Two AIs editing the same
file do not automatically become a good engineering team.

## 2. A prompt is the assignment; context is the case file

Anthropic's guide to context engineering (September 2025) describes context as everything the model
sees while it works, not only the prompt you type. It treats context as a limited resource. Each extra
piece of text uses some of the model's attention, and recall tends to get worse as the
**context window** fills up. The aim is to find the smallest set of useful information that makes the
right result likely.

One technique is "just in time" retrieval. Instead of loading every document at the start, the agent
keeps light references, such as file paths or links, and opens the content when it needs it. The
guide adds that this is slower and needs good guidance, so a mix of preloaded and on-demand
information often works best.

Claude Code's best-practices page makes the same point from the practical side: performance gets
worse as the context fills, so the context window is the most important resource to manage.

Anthropic's newest engineering post, on agent memory (6 November 2026), takes the idea one step
further. It describes memory in layers: full session logs at the bottom, notes and structured pages
in the middle, and a small layer that is loaded into every session at the top. That top layer has to
stay small. The post suggests saving only what cannot be read from the environment each time, such as
plans and rules that have been tested. In one of its experiments, a leaner memory folder did better
than one that logged everything.

In a project, all of this means: rather than asking Claude to "read the whole repo and improve it",
give it a narrow task and the files that own that behaviour. **Narrow down** first, then widen the
scope when you find a real dependency. But do not save tokens by skipping the place where the data is
actually read or written.

## 3. Write a six-line brief

A good **brief** does not need to be long. It needs to state what the AI cannot guess from the code.
Here is the format I suggest, using a bug where a learner's answer disappears after a refresh:

- *Observed problem:* after a refresh, the learner's answer disappears.
- *Expected result:* after a refresh, the same draft opens again.
- *Scope:* the answer component, the storage helper and their direct tests.
- *Invariants:* do not delete older attempts; do not change what "Done" means.
- *Evidence:* type an answer, refresh, reopen the lesson and test a storage failure.
- *Permissions:* edit locally; do not push, deploy or change the database.

An **invariant** is something that must stay true after the change. Listing **invariants** is often
more useful than describing the solution, because it tells the AI what it must not break.

The official best-practices page gives similar advice in more detail: point to specific files,
mention constraints, describe the symptom, and say what "fixed" looks like. One of its examples asks
Claude to write a failing test that **reproduces** the bug, and only then to fix it.

You do not need a "super prompt". You need to make clear what cannot be guessed.

This site uses a version of the same idea. Its repository has a change brief template with sections
for the problem the user can see, the evidence that it is solved, the files that may be edited and
the files that must not be edited. Its project instructions also tell an assistant not to scan the
whole repository unless an audit is requested.

## 4. The loop: a small patch, clear evidence

Claude Code's guide recommends separating research and planning from the code itself: explore, plan,
implement, then commit. Planning has **overhead**, though. The guide's rule of thumb is that if you
could describe the change in one sentence, you can skip the plan.

For a frontend change, this is the checklist I suggest:

1. **Reproduce** the bug before fixing it. Write down the steps and the actual result.
2. Ask the AI to explain the data path. Do not change anything while it is still unclear.
3. Agree on the smallest patch that fixes the cause.
4. Run the relevant checks, read the diff and try the real user flow.
5. Write down what was not checked, and ask for approval before releasing.

Don't merge different kinds of evidence into one word, "Done". A passing build only shows that the
build was created. It does not prove that the microphone works on an iPhone. A storage test does not
prove that a button has enough contrast. A nice screenshot does not prove that an answer survives a
refresh.

The guide is direct about this: give Claude a check it can run, such as tests, a build or a
screenshot to compare, and ask it to show evidence instead of simply claiming success. And when a fix
makes things worse, **roll back** to the last good state rather than stacking new fixes on top.

## 5. CLAUDE.md, skills, hooks and CI: one job each

The guide separates instructions the model reads from mechanisms that tools **enforce**. CLAUDE.md
instructions are **advisory**: the model reads them and usually follows them, but nothing forces it
to. Hooks are **deterministic**: they are scripts that run at fixed points, every time.

![Two groups of controls. Read by the model: the task brief, CLAUDE.md and skills. Enforced by tools: hooks, permissions with a sandbox, and CI with branch rules.](/images/claude-practice/controls-en.png)

Here is how I divide the work:

- *CLAUDE.md* is loaded at the start of every session. Use it for stable facts that Claude cannot
  work out from the code: commands, unusual style rules, how to run tests and project decisions. Keep
  it short. The guide suggests asking of each line whether removing it would cause mistakes, and
  warns that a long file makes Claude miss the rules that matter. **Prune** it regularly.
- *Skills* package knowledge or a repeated procedure, such as an accessibility review. Claude loads
  them when they are relevant, so they do not fill every session. A skill does not turn the model
  into a certified expert.
- *Hooks* run a fixed step, such as a linter after each edit or a check before a turn may end. The
  check itself still has to be correct, and it must not quietly ignore errors.
- *CI and branch rules* protect the release path. Writing "don't deploy" in a prompt does not replace
  a real permission control.

This site follows the same split. Its CLAUDE.md is only a few lines long and imports a separate
instruction file. That file points to a short "work router" document, lists the checks to run after
code changes, and names two project skills, one for coding and one for interface work.

With several AIs, I prefer one owner for the task, one reviewer and a human who approves. The March
2026 post explains why a separate reviewer matters: agents tend to praise their own work, even when it
is mediocre, and it is easier to tune a separate evaluator to be sceptical than to make the builder
criticise itself. The best-practices page adds a warning in the other direction. A reviewer that is
asked to find gaps will usually report some, even when the work is fine, so ask it to flag only
problems that affect correctness or the stated requirements.

## 6. Save money by reducing rework

Most wasted money comes from **rework**: doing the same job twice because the first attempt went in
the wrong direction. These are working choices, not a promise of a fixed saving in tokens:

- Split work by problem and finish criteria, not mechanically by the number of files.
- Read the relevant part first. When you change a data contract, find every place that uses it.
- Before ending a session, write a short **handoff**: the goal, the files changed, the commands run,
  the remaining errors and the next step. Then you can **hand over** the task to a fresh session
  without rereading everything.
- Use scripts for fixed operations. Do not ask a model to compare two lists when a few lines of code
  can do it.
- Measure the time spent reviewing, fixing and recovering, not only the time the AI took to write
  code.

The 2026 posts support the handoff habit. The March post passed a structured handoff file between
sessions so that a fresh agent could continue the work. The November post on memory suggests keeping
a small file with the current goal and next steps, and rewriting it as the work moves on.

The best-practices page also names patterns that waste effort. In the "kitchen sink session",
unrelated tasks fill one conversation; the fix is to clear the context between tasks. If you have
corrected the same mistake twice and it is still wrong, start again with a better first prompt: a
clean session with a better brief usually beats a long one full of failed attempts. Claude Code can
also summarise a long conversation automatically. This **compaction** keeps the important decisions
and frees space, but a clear handoff note is still worth writing.

A short answer that is wrong can cost more than a careful one. The point is not the number of tokens
in one chat, it is the cost of a change you can actually use.

## 7. Security is not "please be careful"

Claude Code's security documentation describes a design based on **permissions**. In its manual mode,
the tool starts with read-only access and asks before it edits files or runs commands that could
change your system. A **sandbox** can isolate commands from the file system and the network. The page
also warns that no system is completely immune to every attack, and says that you are responsible for
reviewing the code and commands you approve.

Two 2026 posts explain why clicking "approve" is not enough. In March, Anthropic reported that users
accepted 93% of permission prompts. When almost everything gets approved, people stop reading what
they approve. This is **approval fatigue**. Anthropic's answer was auto mode, in which a separate
model reviews risky actions before they run. The post is honest about its limits: in their tests the
full system still let through 17% of real overeager actions, and the authors say it is not a
replacement for careful human review on high-stakes infrastructure.

In May, a post on how Anthropic contains Claude across its products set out the deeper principle:
put hard limits at the environment level first. Defences inside the model only make bad behaviour
less likely; a sandbox, limits on network access and keeping credentials out of reach are what stop
data from leaving. The post reports that Claude Code's sandbox cut permission prompts by 84%. It also
treats all outside content as untrusted, because tools can change after you approve them and memory
files can carry instructions into every new session. As the authors put it, "the weakest layer is the
one you built yourself."

One specific risk is **prompt injection**: text in a web page, an issue or a README that tries to give
the AI new instructions. Content that the AI reads is data, not an order from the project owner. The
documentation recommends reviewing suggested commands, not piping untrusted content straight to
Claude, and using virtual machines for scripts that touch external services. It also notes that
Anthropic does not security-audit MCP servers, so use servers you wrote yourself or ones from
providers you trust.

For work projects, my suggestions are simple:

- Use fake data in examples. Do not paste tokens, customer data or internal information unless you
  are allowed to.
- Check your company's policy and the service's settings before sending code outside.
- Give the AI the permissions the task needs, not the maximum because it is convenient.
- Put a real gate in front of actions that change access, delete data or publish something.

Before you approve a command, make sure you understand what it will change. If in doubt, ask for an
explanation first, or **rule out** the risk by running it somewhere isolated.

## 8. Learn Claude and still learn the craft

The four-week cycle below is a practice plan, not an official course or a promise of mastery:

- *Week 1:* take a small bug, describe the symptom, predict the cause, then compare your guess with
  the AI's explanation.
- *Week 2:* write the success criteria and one test before asking for a patch. Read the diff and
  explain it back.
- *Week 3:* practise handoffs. Write a short summary, open a new session and check whether the task
  can continue without rereading everything.
- *Week 4:* try a similar problem on your own first, then ask the AI to review it. Compare how much
  help you needed, not only how many tasks you finished.

After each task, answer three questions. Why did the change belong here? What would break if the
assumption changed? Without AI, would I know how to investigate further?

When you **delegate** a task to an AI, you still keep the responsibility for it.

research says about AI help and skill building.

## Conclusion: good engineers do more than produce code

In the age of AI, the advantage worth building is not knowing more prompts than other people. It is
the ability to define the right problem, limit permissions, read the result and stand behind the
evidence.

A task for today: choose a real but small bug, write the six-line brief from section 3, and let the
AI propose how to check the fix before it changes anything. Only allow the change once you understand
the proposal. At the end, keep one thing you learned and one thing you have not verified, instead of
only writing "done".
