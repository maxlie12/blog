It started with one question: what if I added Hugging Face and free AI models to support learning
on this site? I did not want a chatbot or a clever demo. I wanted to find one small problem that a
free model could really solve.

## 1. The problem

My site has speaking lessons. A learner records an answer, plays it back, and then submits a
written **transcript**. That last step was the weak point. **Retyping** a whole answer on a phone is
slow, and a typed **transcript** often **drifts from** what was really said.

The fix sounds easy: send the audio to a speech-to-text service. The catch is that a recording of
someone's voice is personal data. This site already promises that audio stays in the browser, so
sending it to a **third party** would break that promise. **Privacy** was not a feature to add later.
It was the first requirement.

## 2. The options I looked at

A server API was the obvious choice, but it has two problems: the audio is **uploaded**, and every
minute can cost money on a personal project with no budget. Those two reasons **rule out** most
server options.

The browser's own Web Speech API sounds perfect, but by default it sends audio to a web service
for processing ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_Speech_API/Using_the_Web_Speech_API)).
MDN now also describes an on-device option, which needs a language pack. I have not tested it, and
it may be worth another look.

The third option was the strange one: run the model inside the page. Transformers.js runs models
in the browser with ONNX Runtime, on the CPU through WebAssembly by default
([Hugging Face](https://huggingface.co/docs/transformers.js/index)). That means **inference** happens
on the learner's machine. There is no server to pay for and nowhere for the audio to go. It did mean
one new **dependency**, which is why I load it only when someone asks for it.

## 3. How it works

The flow has five steps:

1. The learner records an answer, and the recording stays in memory.
2. They press "Chép lời trên máy" (transcribe on this device). The button is optional.
3. The page **decodes** the recording into 16 kHz audio, the format Whisper expects.
4. It **hands off** the audio **to** a Web Worker.
5. The worker runs Whisper and sends back a text **draft**, which goes into the answer field.

The model is `onnx-community/whisper-base`, an ONNX version of OpenAI's Whisper Base
([model page](https://huggingface.co/onnx-community/whisper-base)). I use a **quantized** version,
which **shrinks** the files and saves **bandwidth**. The core of the worker is short:

```ts
pipeline("automatic-speech-recognition", "onnx-community/whisper-base", { dtype: "q8" });
```

The worker matters because the main **thread** is the one that draws the page and handles input.
A worker runs in the background, so a heavy job does not block the interface and the page stays
**responsive** ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)).
The audio buffer is also transferred to the worker rather than copied.

## 4. The real numbers

- Encoder and decoder: 23.2 MB and 53.7 MB
- ONNX Runtime WebAssembly: about 20 MB
- Total first download: about 100 MB
- First run, including the download: 61 seconds
- Requests that were not GET: 0
- Library code in the first page load: none (about 870 KB, loaded only by the worker)

So the **upfront** cost is real. It took 61 seconds to finish that first run, and 100 MB is not small
on mobile data. By the time the text appears, though, the model is saved in the browser **cache**,
so it should not need to download again.

These numbers have one big **caveat**: they come from a single test on a desktop browser at phone
width, with a fake microphone playing a synthesized English sentence. It is proof that the idea
works, not a benchmark.

## 5. What it cannot do

The output is a **draft**, not a correction. Whether it is right or wrong, the learner has to
**double-check** it, because the text in the answer field is what gets saved. It writes no Done
record, and it changes no level.

It is not a pronunciation test either. A speech model is built to guess the most likely words,
so it may write the correct word even when my pronunciation was not quite correct.

I have also not tested several things yet:

- **accuracy** with real voices, especially in Chinese and Japanese
- memory and speed on a real phone
- Safari and Firefox

## 6. What I took from this

"AI feature" does not have to mean a chatbot or a monthly bill. Here, the useful work was deciding
the boundary first: the audio stays on the device. That one rule removed most of the options and
made the design simple. A small, boring job, turning speech into a draft, turned out to be a better
first use of AI than something more impressive.

I built this with an AI coding assistant, and the same recorder now also powers the read-aloud
practice on this site.
